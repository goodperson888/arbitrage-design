# 候选监控漏秒与日志修复

日期：2026-11-21，北京时间。本次为监控工程修复，不是新策略回测，不调整策略阈值或用修复后的行情补造历史订单。

## 原因与处理

1. 高频盘口更新每次重建最近30秒价格列表，并重复排序盘口；乱序来源时间戳也使简单队列优化退回全量过滤。最终改为来源时间最小堆清理、到达顺序字典查询，保留重复时间、乱序、五秒前查找和过期边界的原有结果。盘口按侧缓存，完整快照及对应侧增删改时失效。
2. Binance接收到缓存中的大量成交时，异步迭代可能连续执行而不让出控制。增加约5ms处理预算后主动让出，给判断循环运行机会；不改变消息内容或采样频率。
3. 旧候选观察在固定小时gzip文件后继续追加；前一进程未写完尾部时，后续gzip成员使常规读取报错。新进程每小时使用独立唯一分片，持有文件锁并在正常关闭时完成尾部；不继续追加旧文件。
4. 旧停止命令按命令行匹配进程，也匹配到携带完整启动参数的screen/login，可能先关闭终端。现仅通知Python/Node解释器，最多等待约30秒，再关闭screen。候选正常退出时保存最新覆盖计数。

所有候选方向公式、0.30–0.50决策价格范围、270–30秒窗口、两秒新鲜度、预算、费用、至少300ms执行延迟及逐秒判断规则均不变。保持原账户ID与冻结指纹，累计统计不重置。

## 验证

- 113项相关测试、5个子测试通过。包含原策略、六候选、盘口深度、费用、重启恢复、未知指纹拒绝、随机乱序/重复时间戳与旧动量逐点对照、缓存失效、Binance突发调度、解释器进程选择，以及压缩恢复与备份。
- 固定16000条盘口更新、每条两处变动、40秒来源时间轴并插入乱序：旧实现17.992秒，最终实现0.980秒，约18.4倍；保留历史、盘口价格/深度和动量结果相同。这是本机固定负载耗时，不代表交易网络提速18倍。
- 单独的短时实时采样曾无新增漏秒，但持续运行暴露乱序退化，因此以最终实现的更长在线观察作为验收，不以短时样本保证长期零漏秒。

最终版本于北京时间18:51:41启动；18:54:42检查时已连续运行约182秒，Polymarket及候选Binance均为`live`，无候选异常。历史累计漏秒保留1907，观察期间新增0；旧十二账户的资金、胜负、档位、费用及启用时间均核对保留，A5固定/倍投仍各为同一次机会的1胜、净收益各0.931225U。原策略原有待结算订单收到官方结果后正常推进统计，不把自然新增结算当作重置。

三个修复分区使用标准gzip重新读取，共5093条；修复期间新生成的两个已关闭分片也能完整解压，当前活跃分片通过带写入锁判断的读取器正常读取。此次只恢复`paper`服务，其余独立采集器未启动，无实盘订单。

## 以后如何操作

正常启动、停止仍用以下命令，无需另开压缩服务：

```sh
./arb-monitor start paper
./arb-monitor status
./arb-monitor stop paper
```

仅在明确发现离线候选观察损坏时使用修复工具。先停止paper；不允许修复正在写入的候选目录：

```sh
./arb-monitor stop paper
.venv/bin/python scripts/utils/repair_candidate_observations.py
.venv/bin/python scripts/utils/repair_candidate_observations.py --apply
./arb-monitor start paper
```

不带`--apply`仅预览。带`--apply`先备份原文件，再发布已验证的修复结果。不能解压或发现完整JSON行错误时停止报错，不静默跳过；符号链接和过大文件被拒绝。工具只处理候选观察，不接触账户交易账本。
