# Polymarket BTC 5分钟实盘自动交易方案

状态：方案评审中，暂未创建真实下单程序，也未启用任何真实订单。

当前候选组合的统一口径见：[实盘候选策略组合 V1](实盘候选策略组合_v1.md)。该文档只整理研究结果，不代表已经启用真实下单。

## 1. 目标策略（第一版）

这是当前研究结果中最值得做实盘小额验证的候选，不是稳赚承诺：

1. 只交易 Polymarket BTC 5分钟市场的 DOWN。
2. 只接受真实主动成交事件作为触发，不用单纯报价触发。
3. 剩余时间 90–30 秒。
4. 每笔最大预算 5U，实际下多少由当时盘口决定；有效成交金额至少 2.5U。
5. 预计实际成交 VWAP 0.80–0.85，最坏可成交价不超过 0.85。
6. 入场前 5 秒，DOWN 合约价格不出现至少 0.01 的逆向回落。
7. Binance Spot 最近 5 分钟方向与 DOWN 一致。
8. 每个市场最多一笔，不追单、不反向补仓。
9. 第一版持有到官方结算，不自动中途卖出。

`VWAP 0.81–0.82` 和 15 秒动量属于高边际候选，当前样本太少，只做影子统计，暂不写进第一版实盘硬条件。

## 2. 为什么必须独立目录

现有 `arbitrage-research` 是研究、采集、纸上交易和回测项目；其架构边界明确禁止成为真实执行依赖。实盘程序应放在同级目录：

## 4. 运行模式与上线闸门

任何默认命令都不能下真实订单，必须显式指定模式：

| 模式 | 钱包/密钥 | 行为 |
|---|---|---|
| `observe` | 不需要 | 只采集行情和计算信号 |
| `shadow` | 不需要 | 可选模拟模式；本次不作为上线前置条件 |
| `canary` | 需要 | 小额真实订单，单笔和每日上限极低 |
| `live` | 需要 | 仍受全部风险上限和急停保护 |

按本次方案采用 `observe → canary → live`，不强制运行 shadow。第一次真实运行仍使用 canary 限额；每次启动都记录模式、配置哈希、代码版本和密钥标识摘要，不记录私钥原文。

## 5. 订单执行语义（FAK部分成交）

FOK 和“允许少量成交”是两种不同的成交模型。本次按用户确认，采用“预检 + 单次 FAK”：计划金额上限5U，实际成交金额低于2.5U则视为无效小额成交；不自动补单。

1. 收到 Polymarket 主动成交信号。
2. 读取最新盘口，检查时间、tokenId、方向、价格、深度和 Binance 条件。
3. 计算最多5U的预计吃单均价、最大可买数量和最坏价。
4. 预计最坏价超过 0.85、盘口陈旧、数量不足或余额不足，直接拒绝。
5. 使用一次 FAK买入请求，按实际可用数量成交，剩余立即取消；不对同一市场自动重复追单。
6. 通过订单状态和成交接口确认 `matched/partial/canceled/rejected`，把实际数量、金额和每个状态写入账本。
7. 发现未知状态时先暂停该市场，不盲目重发，直到对账完成。

FAK允许部分成交，但会改变交易数量、手续费、滑点和机会统计，因此必须使用固定金额/部分成交执行模型，不能直接套用固定10份完整成交回测。Polymarket 官方文档列出的订单类型包括 GTC、FOK、GTD 和 FAK，订单状态和成交历史应通过官方接口对账。

## 6. 必须有的风控

- 只允许 BTC 5分钟市场、DOWN tokenId 白名单。
- 每市场最多一笔；禁止同市场同时 UP/DOWN。
- 单笔最大成本、每日最大成本、最大未结算持仓、最大连续失败次数。
- 日亏损达到上限立即停止新订单。
- 每日出现2笔亏损或累计亏损达到10U，任一条件先满足即停止新订单；次日需人工确认恢复。
- Binance 或 Polymarket WS 断线、延迟超时、时间不同步时禁止下单。
- 订单状态无法确认时禁止重试。
- 程序异常退出时默认不恢复下单，只恢复为 `observe` 并等待人工确认。
- 本地急停文件/命令优先级高于策略：触发后取消可取消订单、停止新订单、保留对账进程。
- 密钥只放 macOS Keychain/环境注入，不放 JSON、`.env`、日志、git 或页面。

## 7. 需要记录的真实交易数据

每个信号都记录，无论成交还是拒绝：

- marketId、conditionId、tokenId、方向、剩余秒数；
- 触发事件时间、本机接收时间、下单时间、交易所响应时间；
- 触发时的 Polymarket 多档盘口、Binance 5分钟动量和信号版本；
- 请求数量、限价、预计 VWAP、预计最坏价；
- orderId、订单类型、状态变化、拒绝原因；
- 每一笔 fill 的数量、价格、手续费、交易ID；
- 实际成交数量、实际 VWAP、部分成交率；
- 结算赢家、结算时间、最终净收益；
- 余额和持仓快照、程序版本、配置哈希。

实盘数据和纸上数据分开目录、分开数据库、分开报告；后续回测可以对照，但不能直接合并成一个样本。

原始行情和高频快照先进入内存有界队列，由独立 writer 异步写入；不在下单关键路径同步写整份原始盘口。订单请求/响应、fill、拒单和结算属于关键账本事件，写入失败时停止新订单。程序记录队列深度、丢弃数和 p50/p95 写入延迟，评估记录是否影响下单速度。

## 8. 第一阶段不做的事

- 不自动交易 UP。
- 不自动中途卖出。
- 不要求 Binance、Futures、Hyperliquid、Deribit 三方全部同向。
- 不把 `0.81–0.82` 小样本结果写成硬门槛。
- 不用实时页面点击作为下单路径。
- 不在研究项目里保存私钥或直接调用真实下单接口。
